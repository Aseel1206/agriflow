# AGRIFLOW —  HACKATHON MVP

We have only 3 days to build the MVP.
Do NOT over-engineer the project.
The priority is:

Build ONE complete, polished, working agricultural marketplace platform from frontend to backend to database.

The platform has three user roles:

1. FARMER (individual, or member of an FPO — see §11a)
2. BUYER / MARKET
3. LOGISTICS PROVIDER

All three users should use the web application for the MVP.
Do NOT implement voice, IVR, WhatsApp, mobile apps or other farmer-access mechanisms yet.
However, keep the backend architecture extensible so these can be added later.

 CORE PRODUCT

The platform connects:

FARMER
   ↓
Agricultural Supply
   ↓
AI TRADE ENGINE
   ↑
Agricultural Demand
   ↑
BUYER / MARKET

LOGISTICS PROVIDER
   ↓
Shared transportation
   ↓
Optimized route


The main innovation is:
The system does not optimize only for selling price. It finds the best transaction considering price, transport cost, quantity, distance, shelf life and buyer requirements.

The platform should produce a:

# BEST TRADE

for each farmer/buyer combination.


KEEP THE AI SIMPLE

We only need TWO intelligent components for the MVP.

Use one ML service/interface.

5. SHELF LIFE

Do NOT train a shelf-life model.

Use a simple rule-based system.

Each crop has a default shelf life.

Example:

```text
Tomato → 5 days
Onion → 30 days
Potato → 60 days
Banana → 7 days
Cabbage → 14 days
```

Calculate:

```text
remaining_shelf_life =
default_shelf_life - days_since_harvest - estimated_transport_time
```

Generate:

```text
freshness_score
```

from the remaining shelf life.

Keep this in a separate:

```text
FreshnessService
```

so an ML model can replace it later.

# 6. DEMAND

Do NOT build a demand forecasting ML model from scratch for the MVP.

UPDATE: a real trained LightGBM model (regional mandi arrivals forecast,
748 trees, ~638k historical rows 2001-2021) was contributed separately —
see /demand_model at the repo root for training notes, and
backend/app/services/demand_forecast_service.py for the integration and
its honesty caveats (it predicts arrivals as a market-activity proxy, not
literal buyer demand, and two of our five seed crops aren't in its
training vocabulary). It's wired in as a clearly-separate "Regional Market
Outlook (Forecast)" section on the Market page — GET /market/demand-forecast
and POST /ai/demand/predict — and must never be visually merged with the
live numbers below, which remain untouched.

Demand for the MVP's live Supply vs. Demand numbers still comes directly
from buyer requirements, unrelated to the forecast above.

# 7. NET REALIZATION

This is a core business calculation.

For a farmer:

```text
Net Realization =
Sale Value
- Transport Cost
- Handling Cost
- Expected Spoilage Cost
```

Example:

```text
Sale price       ₹38/kg
Transport        ₹1.5/kg
Handling         ₹0.5/kg
Spoilage          ₹1/kg
-------------------------
Net realization  ₹35/kg
```

The platform should optimize for this number.

# 11a. FPO (FARMER PRODUCER ORGANIZATION)

The official problem statement explicitly says "farmers/FPOs" — the platform must
support FPOs, not just individual farmers.

An FPO is modeled as a farmer-aggregator account:

```text
fpo_profiles
    → many farmer_profiles (via optional fpo_id on farmer_profiles)
```

FPO account gets:

```text
Same dashboard as an individual farmer
+
Roll-up view of all member farmers' listings, offers and earnings
```

This requires no new matching/aggregation logic — an FPO's member farmers already look
like "multiple farmers contributing to one Virtual Supply Lot" (§11), so the existing
aggregation engine handles FPOs for free.

Seed data (§26) should include 2–3 demo FPOs grouping a subset of the 50 farmers.
